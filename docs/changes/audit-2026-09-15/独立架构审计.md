# Independent architecture audit of RoboTenon

Audit date: 2026-09-15. The audit examined the RoboTenon Python implementation in the workspace before repairs.

> This report and source-sha256.json establish the pre-repair baseline. The implementation was subsequently refactored. The old line numbers and reproduce.py allow historical comparison. Current checks use tests/test_architecture_regressions.py. See ../migration-2026-09.md for changes.

## Conclusion

**Retain the four-service architecture and refactor it incrementally. Execution semantics and safety state invariants take priority over splitting files.**

Workflow makes decisions, Body executes actions, Environment supplies feedback, and Monitor observes safety conditions. These responsibilities can evolve independently. Other designs worth retaining include resident Modules, per-Run environment Sessions, distinct protocols and in-process/UDS implementations, and bounded observability client queues.

The implementation did not yet satisfy all documented guarantees for parallel execution, loops, resumption, and latching. The audit reproduced five classes of defect. Passing the existing tests did not establish the production behavior of all four services.

## Scope and verification

- Reviewed workflow, services, runtime/safety, core/context, modules, and application assembly. Spot-checked the queue, observability, Web, extension dependencies, and plugin documentation.
- The audit assessed the code independently of earlier conclusions in embodied-design/audit-v2. Design materials were not evidence of implementation correctness.
- Python 3.11.10 and Pydantic 2.13.5: **57 passed, 1 skipped**. The sandbox disallowed socket binding, so the UDS test was skipped. LangGraph was absent, which limited coverage to the fallback/custom scheduler.
- Both modules-check and graphs-check returned ok.
- A standalone diagnostic script, reproduce.py, reproduced all five defects and checked safety latching with both the in-memory and SQLite implementations.
- The audit changed no runtime code. This directory contains audit artifacts only. Scope excluded physical robots, load testing, real cross-process fault injection, and dependency version matrices.
- The project directory was untracked in the outer Git repository. In lieu of a commit identifier, source-sha256.json records the source hashes.

## 1. Correctness issues requiring priority fixes

P1 indicates an issue to address before further runtime expansion or physical deployment. Each finding includes supporting code and a minimal reproduction.

### F1 · P1: A subsequent signal with the same name can overwrite a P3/P4 latch

Locations: robotenon/runtime/safety.py:109 (in-memory update) and :374 (SQLite update).

Both implementations overwrote records by signal.code. They set latched for incoming P3/P4 signals without preserving the previous latch for the same code. After `raise_level(P3, code='monitor.compliance')`, a P1 update with that code produced **P1, latched=False** without a recover call or approval.

Impact: If continuous monitoring first reports a severe fault and then a milder one, the original event can lose its requirement for explicit recovery. Body and Workflow may subsequently admit ordinary actions.

Recommendation: Store current observations separately from unacknowledged safety events. An ordinary update must preserve the latch level of an unacknowledged event. Use the same transition rules and contract tests for in-memory and SQLite backends.

Acceptance: P3 followed by P1/P0 with the same name, P4 followed by P3 with the same name, identically named signals from different sources, and concurrent update/recover operations must all preserve the explicit recovery requirement.

### F2 · P1: The second loop iteration skips its predecessor barrier

Location: robotenon/workflow/runtime.py:719–737.

The completed set retained previous iterations. After a back edge, the scheduler scanned all nodes and released successors when every predecessor had completed at some point. It neither limited completion to the current iteration nor limited the scan to direct successors of the current node.

Reproduction: `policy → action → judge → goto policy`. The first iteration ran in order. The second produced `action enter → judge enter → judge exit → action exit` in history. The judge ran before the current action completed, despite its explicit dependency on action.

Impact: Evaluation may read a prior action and its feedback and decide prematurely to stop or start the next action. Existing self-loop tests do not exercise dependencies inside multi-node loops.

Recommendation: Key predecessor completion by activation_id or iteration. Build a successor index at compile time and release only direct successors ready in the current activation. Define the rules for branches, joins, loops, and END.

Acceptance: Verify the per-iteration barrier for a two-pass chain, fork/join inside a loop, reconverging conditional branches, and a slow action paired with a fast evaluator.

### F3 · P1: Parallel subgraphs share a call stack and can appear recursive

Locations: robotenon/workflow/runtime.py:592 (_run_graph), :710 (gather), and :835 (node execution context).

When two peer nodes called the same child graph concurrently, the first wrote the child to shared ctx.graph_stack. The second treated that entry as recursion. The minimal example returned `failed: recursive graph invocation detected` despite the independence of the branches.

In addition to application values, the branches shared current_node, current_graph, step, history, and the call stack. Even Modules writing distinct application keys could interfere through runtime state.

Recommendation: Retain common Run-level application state and give each branch an ExecutionFrame containing its graph path, node_id, call stack, and activation identifier. Concurrent Modules should read a stable view and return NodeResult. The scheduler should merge writes under explicit key-conflict rules. Serializing stateful writes or service side effects is one possible transition step.

Acceptance: Concurrent branches can call the same subgraph, true recursion is rejected, and events identify the correct graph path and activation.

### F4 · P1: Mid-run checkpoints do not resume execution at the saved position

Locations: robotenon/workflow/runtime.py:563 (load snapshot), :592 (stack check), :835 (persist node), and core/context.py:150 (CAS save).

A checkpoint saved after a node retained the active graph_stack. In the reproduction, first completed and second blocked. After cancelling the Run, a fresh GraphContext with the same session_id loaded `graph_stack=['checkpoint']` and failed the recursion check.

Clearing graph_stack alone would not persist pending, completed, outstanding goto transitions, or loop iterations. The entry point still starts at graph.entry. **Restoring application fields and resuming execution at a specific position require distinct mechanisms.** CAS prevents overwriting a newer version but gives no guarantee against replaying side effects.

Recommendation: Define a RunCheckpoint with schema_version, graph/config versions, cursor, and activation state. Treat transient call stacks separately. Define which nodes are replayable and reconcile action nodes using a stable idempotency_key and Body acknowledgement. Until implemented, document the supported operation as loading a state snapshot.

Acceptance: Interrupt and resume at each node boundary. Verify the cursor, incompatible graph versions, action retries, and unconfirmed outcomes in addition to final snapshot round trips.

### F5 · P1: execute blocks interrupt on the same remote Body client

Locations: robotenon/services/ipc.py:92–103 and BodyServiceClient.execute/interrupt.

JsonRpcClient held one lock across the entire request and response. interrupt and health waited for an outstanding execute on the same client. The request timeout started after lock acquisition, leaving the acquisition wait unbounded.

An in-memory transport substitute exercised the real JsonRpcClient.call. While execute was waiting for a response, it was the only method written. interrupt was written only after execute was released. This test required no UDS bind. Real end-to-end, cross-process verification was still outstanding.

Impact: The remote client did not preserve the in-process Body's concurrent interrupt behavior. A Supervisor sharing the client could mistake a long-running action for a failed service. The Body watchdog provides separate protection, but does not restore explicit interrupt semantics.

Recommendation: Give the Body client a separate control connection for interrupt/health, or multiplex RPC with request_id dispatch. Handle cancellation cleanup, the overall deadline, and actions still running on the server consistently.

Acceptance: During a long execute, issue interrupt and verify that the stop callback runs before normal action completion. health must remain responsive, and cancellation must not misassociate the next response.

## 2. Modularity, readability, and maintenance

### 1. Consolidate the execution core

There were two execution paths, a fixed LangGraphWorkflow and a JSON GraphRuntime. The latter included a custom predecessor scheduler, a legacy edge fallback, and a LangGraph path. The fixed Workflow integrated TaskQueue operations, SafetyGate, Evaluator safety merging, and Recorder. The JSON Graph path had different responsibilities and behavior.

For example, the fixed Workflow restricted P2 actions with SafetyGate, while Body mainly checked the P3 interruption threshold by default. GraphContext.record_output primarily stored EvaluationDecision and did not perform the same queue and safety operations. Document these differences explicitly.

Recommendation: Make JSON Graph the long-term entry point, expressing the fixed loop as a Graph template with explicit task and evaluation operations. Convert compatible formats to a common internal representation (IR) when loading, then converge on one set of scheduler and safety semantics. Document capabilities and add compatibility tests before retiring older paths.

### 2. Split GraphRuntime by responsibility

The 1153-line runtime.py combined GraphContext, serialization, expression evaluation, multiple scheduler backends, service dispatch, persistence, emergency handling, and recovery. A change to any part required understanding state transitions elsewhere.

The following boundaries can be introduced incrementally as the affected code changes.

| Boundary | Responsibility | Constraint |
| --- | --- | --- |
| contracts | Action/Feedback, RunState, NodeResult, Checkpoint, service protocols | Independent of workflow and storage implementations |
| workflow/compiler | Format compatibility, reference validation, condition compilation, successor index | Does not send actions or write state |
| workflow/scheduler | Activations, branches, joins, loops, ExecutionFrame | Independent of SQLite and UDS |
| workflow/operations | Handlers for env/body/monitor/task operations | Depends on explicit service interfaces |
| workflow/runtime | Run lifecycle and orchestration of these components | Algorithms live in the responsible components |
| safety | Signal merging, latching, recovery authorization, action admission | One contract across storage backends |
| storage | SQLite implementations of context, safety, and the action ledger | Implements interfaces in contracts |
| bootstrap | Configuration, registration, dependency injection, startup and shutdown | Sole location for selecting concrete implementations |

### 3. Separate shared application state from execution state

ctx.values automatically merged every dict output, and ctx.outputs was keyed only by node_id. Application keys and same-named nodes in nested graphs could overwrite each other. Dynamic Any values and implicit side effects also obscured each node's reads and writes for plugin authors.

Recommendation: Introduce a stable NodeResult (outputs/state_patch/decision), identifying outputs by graph path and activation_id. Type important state and reserve values as a controlled extension area. Additional global ctx fields would compound the coupling.

### 4. Standardize the Module invocation contract

The Module protocol in modules/base.py declared only invoke. The factory accepted run/invoke, GraphRuntime expected run(GraphContext), and ModuleRuntime.call could pass ModuleContext to run. Registration alone did not guarantee executability at every entry point.

Recommendation: Distinguish GraphModule from CallableModule or use one input contract with an adapter for legacy invoke. Validate capabilities at compilation/assembly so errors surface at startup. Lifecycle rollback also needs to cover failure, cancellation, and close errors.

### 5. Remove dependencies from lower layers back into workflow and remove import side effects

The Environment and Monitor servers in services/ipc.py imported workflow.runtime.GraphContext to decode requests, coupling service implementations to scheduling. Use independent request DTOs instead of passing the entire mutable GraphContext.

robotenon/__init__.py imported much of workflow, services, and queue, then registered built-ins. Importing safety/context read environment variables and could create SQLite files. Keep package imports small, select stores and register components in bootstrap, and inject defaults explicitly. This allows isolated tests of multiple instances.

Serialization was duplicated in workflow/runtime.py, services/ipc.py, and elsewhere. Unknown types degraded to str, and failed model restoration could return None. Use a single strict codec with actionable errors for unknown structures and define checkpoint versions and migrations.

### 6. Define observability and UI boundaries

Retain bounded Metrics/Trace client queues. The client and daemon/exporter can be split when those files next change. GraphContext.history grew indefinitely, and each node synchronously saved the entire context. Separate append-only events from compact state snapshots to limit serialization and SQLite costs in long loops. Distinguish essential persistence from expendable telemetry.

The SQLite store called synchronous connections/transactions from asyncio paths. The context connection used a 5-second busy_timeout. No load measurements were taken. Measure lock contention and tail latency before hardware timing acceptance. poll_hz=100 alone does not guarantee a 100Hz control period.

The 527-line web/server.py handled Docker/Grafana startup, HTTP, queries, and embedded HTML/CSS/JS. Separate server, query_service, grafana_launcher, and static assets. A new frontend framework is unnecessary for this change.

## 3. Recommended implementation order

| Stage | Change | Acceptance criterion |
| --- | --- | --- |
| 1. Stabilize behavior | Fix F1–F5 and convert reproductions into regression tests for expected behavior | Tests establish latch, loop, parallel subgraph, interrupt, and resume semantics |
| 2. Consolidate contracts | Introduce ExecutionFrame/NodeResult/RunCheckpoint, independent safety rules, and request DTOs | Scheduler independent of storage, services independent of workflow, and typed plugin entry points |
| 3. Consolidate the core | Migrate the fixed loop to a template and normalize legacy formats when loading | Common scheduler semantics with a compatibility layer and capability matrix for old APIs |
| 4. Reorganize implementation | Simplify imports, separate static assets and observability daemons, and update documentation | Ordinary imports allocate no resources, examples run, and ownership is clear |

Commit each stage independently and separate behavioral fixes from file moves. Prioritize fault-model tests. Consider import-boundary and type checks plus CI with and without LangGraph, the minimum supported Python, and supported Pydantic versions. Narrow the declared support range explicitly if the matrix becomes too expensive to maintain.

## 4. Reproduction

From the RoboTenon root, use Python >=3.10 with the project dependencies installed.

```bash
python docs/changes/audit-2026-09-15/reproduce.py
```

The script uses a temporary SQLite database and an in-memory RPC substitute. It does not call hardware. It asserts the defects observed in this audit. After repair, convert these into positive behavior assertions for the regression suite.
