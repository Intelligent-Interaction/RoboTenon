# RoboTenon 独立架构审计

审计日期：2026-09-15。对象：修复前工作区的 RoboTenon Python 实现。

> 此报告与 source-sha256.json 是修复前基线。代码已按报告重构；旧行号和 reproduce.py 用于历史对照。当前验证使用 tests/test_architecture_regressions.py，变更见 ../migration-2026-09.md。

## 结论

**总体边界合理，建议保留四服务架构并渐进重构。当前最需要修复的是执行语义和安全状态不变量，其次才是文件拆分。**

Workflow 负责决策、Body 负责动作、Environment 负责反馈、Monitor 负责安全观察，这些职责适合独立演进。模块常驻、环境 Session 按 Run 管理、协议与进程内/UDS 实现分开，以及观测客户端使用有界队列，都是值得保留的设计。

但实现尚未完整支撑文档中的并行、循环、断点恢复和锁存承诺。本次确认了五类可复现问题。完成这些修复前，不宜将“已有测试通过”视为四服务生产运行语义已经验证。

## 一、优先修复的正确性问题

以下 P1 表示应在继续扩展运行时或真实部署前优先修复；各项均有代码证据与最小复现。

### F1 · P1：同名新信号可以覆盖 P3/P4 锁存

位置：robotenon/runtime/safety.py:109（内存 update）、:374（SQLite update）。

两个实现均按 signal.code 覆写已有记录，只对“新信号”的 P3/P4 设置 latched，没有保护同名旧信号的锁存状态。实际执行 `raise_level(P3, code='monitor.compliance')` 后，再提交同 code 的 P1，状态变为 **P1、latched=False**，没有调用 recover 或传入批准。

影响：持续监控先报告严重故障、后报告较轻故障时，可绕开显式恢复要求。Body 和 Workflow 随后可能重新允许普通动作。

建议：把“当前观测信号”和“未确认的安全事件”分开保存；普通 update 不能删除或降低未确认事件的锁存等级。内存与 SQLite 共用同一套状态转换规则，并对两种后端运行同一组契约测试。

验收：P3→同名 P1/P0、P4→同名 P3、不同来源同名信号，以及并发 update/recover 都不能隐式解除锁存。

### F2 · P1：循环第二轮会跳过本轮前驱屏障

位置：robotenon/workflow/runtime.py:719–737。

completed 集合保留了上一轮完成记录；回跳节点完成后，又遍历所有节点，以“历史上全部前驱曾完成”为条件释放后继，未绑定当前轮次，也未限定为当前节点的直接后继。

复现：`policy → action → judge → goto policy`。第一轮顺序正常；第二轮 history 为 `action enter → judge enter → judge exit → action exit`。judge 在本轮动作完成前已经执行，即使图明确声明 judge 的前驱为 action。

影响：评估可能读取上一轮动作结果和反馈，提前决定结束或下一轮动作。现有自循环测试无法覆盖多节点循环的依赖语义。

建议：使用 activation_id/轮次标识前驱完成状态；编译阶段建立后继索引，调度器只释放满足本次激活条件的直接后继。明确分支、汇聚、循环与 END 的规则。

验收：单链两轮、循环内 fork/join、条件分支后汇聚、慢 action 与快 evaluator 的组合都保持本轮屏障。

### F3 · P1：并行子图共用调用栈，正常调用被判定为递归

位置：robotenon/workflow/runtime.py:592（_run_graph）、:710（gather）、:835（节点执行上下文）。

两个同层节点并发调用同一个 child graph 时，第一个子图把 child 写入共享 ctx.graph_stack；第二个子图据此判断出现递归。最小复现返回 `failed: recursive graph invocation detected`，实际两个分支不存在递归关系。

不仅业务 values 共享：current_node、current_graph、step、history 和调用栈也全部共享，模块即使只写不同业务 key，仍不能避免运行时自身的并发干扰。

建议：保留 Run 级统一业务状态，但引入每个分支独立的 ExecutionFrame（图路径、node_id、调用栈、激活编号）。并行模块读取稳定视图、返回 NodeResult；调度器统一合并写入，冲突 key 必须有显式策略。先将有状态写入或服务副作用节点串行化，也可作为过渡措施。

验收：同一子图在两个并行分支调用成功；真实递归仍被拒绝；节点事件能够归属到正确图路径和激活实例。

### F4 · P1：中途 checkpoint 无法按承诺恢复执行

位置：robotenon/workflow/runtime.py:563（恢复快照）、:592（图栈检查）、:835（节点持久化）；core/context.py:150（CAS 保存）。

节点结束后保存的 checkpoint 含有仍在执行的 graph_stack。复现中 first 完成、second 阻塞时取消 Run，用同 session_id 的新 GraphContext 启动，会加载 `graph_stack=['checkpoint']`，随后被判定为递归并失败。

即使简单清空 graph_stack，pending、completed、等待中的 goto、循环轮次等调度状态也未持久化，运行入口仍从 graph.entry 开始。**恢复业务字段与恢复执行位置是两个不同能力**；CAS 只阻止旧版本覆盖新版本，不能保证副作用不会重放。

建议：定义带 schema_version、graph/config 版本、执行游标和激活状态的 RunCheckpoint；瞬时调用栈独立处理。明确恢复后哪些节点可以重放，动作节点结合稳定 idempotency_key 与 Body ack 对账。能力完成前，将文档承诺限定为“状态快照加载”。

验收：在每个节点边界中断并恢复；验证游标、图版本不兼容处理、动作重试与未确认执行结果，避免仅测试最终快照 round-trip。

### F5 · P1：同一个远程 Body client 的 interrupt 被 execute 阻塞

位置：robotenon/services/ipc.py:92–103、BodyServiceClient.execute/interrupt。

JsonRpcClient 持有整段请求/响应锁。execute 未返回时，同一 client 发出的 interrupt 和 health 必须等待 execute 释放锁。请求超时从获得锁后才开始计算，无法约束锁等待。

本次用内存替身驱动真实 JsonRpcClient.call：execute 等待响应期间发起 interrupt，实际写出的 method 只有 execute；释放 execute 后 interrupt 才写出。该验证不需要 UDS bind，但尚未执行真实跨进程端到端验证。

影响：进程内 Body 可并发响应 interrupt，远程 client 却无法保持该语义。共享 client 的 Supervisor 探活也可能将正常长动作误判为服务故障。Body 自有 watchdog 是另一条保护路径，但不能修复显式 interrupt 的协议行为。

建议：让 Body client 内部提供独立控制连接，interrupt/health 不排队在 execute 后；或实现带 request_id 分发的多路 RPC。统一处理取消后的连接清理、总 deadline 和服务端未结束动作。

验收：在长 execute 中发 interrupt，确认 stop 回调在动作正常完成前执行；执行期间 health 可响应；取消请求后下一次响应不会错配。

## 二、模块化、可读性和可维护性

### 1. 收敛执行内核：收益最高

目前实际存在固定 LangGraphWorkflow，以及 JSON GraphRuntime；后者又包含 predecessor 自研调度、legacy edges fallback 和 LangGraph 路径。固定 Workflow 有 TaskQueue 操作、SafetyGate、Evaluator 安全合并与 Recorder 接入；JSON Graph 路径的职责与行为并不等价。

例如固定 Workflow 用 SafetyGate 对 P2 动作做限制，而 Body 默认主要检查 P3 中断阈值；GraphContext.record_output 对 EvaluationDecision 主要做存储，未实现固定 Workflow 中同样的队列操作与安全处理。这些差异应明确列出，不应靠“都叫 Workflow”暗示等价。

建议确定 JSON Graph 为长期主路径，把固定闭环表达为图模板及明确的任务/评估系统操作。兼容格式在加载时转换为统一 IR（运行时内部图结构），逐步只保留一套调度和安全执行语义。迁移前先补能力对照表与兼容测试，避免直接删除旧路径。

### 2. 按职责拆分 GraphRuntime

runtime.py 共 1153 行，包含 GraphContext、序列化、表达式解释、多个调度后端、服务操作分派、持久化、紧急处理和恢复。问题不只是文件长，而是修改任何一项都需要理解其他状态变化。

建议职责如下，按修改需要渐进迁移，不必一次性建满目录：

| 边界 | 职责 | 约束 |
| --- | --- | --- |
| contracts | Action/Feedback、RunState、NodeResult、Checkpoint 与服务协议 | 不依赖 workflow 或存储实现 |
| workflow/compiler | 格式兼容、引用校验、条件预编译、后继索引 | 不发动作、不写状态 |
| workflow/scheduler | 激活、分支、join、循环、ExecutionFrame | 不感知 SQLite 和 UDS |
| workflow/operations | env/body/monitor/task 操作处理器 | 依赖明确的服务接口 |
| workflow/runtime | Run 生命周期与上述组件编排 | 不再内嵌全部算法 |
| safety | 信号合并、锁存、恢复授权、动作准入规则 | 一份语义，多种存储后端 |
| storage | SQLite context、safety、action ledger 实现 | 实现 contracts 中的接口 |
| bootstrap | 配置读取、注册、依赖注入、统一启停 | 唯一选择具体实现的位置 |

### 3. 分离共享业务状态与执行状态

ctx.values 自动合并所有 dict 输出、ctx.outputs 仅使用 node_id，会使业务 key 和父子图同名节点的输出互相覆盖。动态 Any 与隐式副作用也让插件作者难以知道某节点究竟读写什么。

建议至少引入稳定的 NodeResult（outputs/state_patch/decision），输出使用图路径与 activation_id 定位；为重要状态建立类型，values 仅作受控扩展区。不要通过再加更多全局 ctx 字段解决模块通信。

### 4. 统一模块调用契约

modules/base.py 的 Module 协议只声明 invoke；factory 同时接受 run/invoke；GraphRuntime 要求 run(GraphContext)，而 ModuleRuntime.call 又可能给 run 传 ModuleContext。插件能注册成功，不代表可在每个入口执行。

建议显式区分 GraphModule 与 CallableModule，或统一一个输入契约并用适配器兼容旧 invoke。编译/装配时校验模块能力，让错误发生在启动阶段，而不是运行到节点后。生命周期回滚也应覆盖失败、取消及 close 异常。

### 5. 去掉低层对工作流的反向依赖与导入副作用

services/ipc.py 的 Environment/Monitor server 导入 workflow.runtime.GraphContext 来解码请求。这让服务端实现依赖调度层；服务协议应使用独立的请求 DTO，而非整个可变 GraphContext。

robotenon/__init__.py 广泛导入工作流、服务、队列，并立即注册内置组件；safety/context 在导入时读取环境变量，可能创建 SQLite 文件。建议精简包入口，注册和 store 选择放入 bootstrap，默认参数使用显式注入。这样可以分别测试多个运行实例，也避免“import 就改变运行环境”。

序列化在 workflow/runtime.py、services/ipc.py 等处重复，未知类型退化为 str，模型恢复失败可能返回 None。建议统一严格 codec，未知结构给出可定位错误，checkpoint 增加版本与迁移策略。

### 6. 让可观测性和 UI 有清楚的边界

Metrics/Trace 的有界入队设计应保留。客户端与 daemon/exporter 当前同文件，可在后续修改时拆开；并非必须为了目录整齐立即重写。GraphContext.history 不断增长、每节点同步保存整个 context，长循环下会增加序列化与 SQLite 成本，应将追加事件与紧凑状态快照分开，并明确关键持久化与可丢弃观测的差别。

SQLite store 使用同步连接/事务，直接在 asyncio 路径调用，其中 context 连接有 5 秒 busy_timeout。未做负载测量，不能据此给出延迟数值；但在真机节拍验证前，需要测锁竞争和尾延迟，不宜把 poll_hz=100 等同于实际 100Hz 时序保障。

web/server.py 共 527 行，同时负责 Docker/Grafana 启动、HTTP、数据查询、内嵌 HTML/CSS/JS。建议拆为 server、query_service、grafana_launcher 与静态资源；现阶段无需为此引入复杂前端框架。

## 三、推荐实施顺序

| 阶段 | 改动 | 完成标准 |
| --- | --- | --- |
| 1. 稳定行为 | 修复 F1–F5；将复现转为期望正确行为的回归测试 | 锁存、循环、并行子图、中断与恢复语义有测试证明 |

每阶段独立提交，行为修复和纯文件搬迁分开。优先增加针对故障模型的测试，而非围绕每个辅助函数堆叠测试。建议加入 import 边界检查、类型检查，以及有/无 LangGraph、最低支持 Python、Pydantic 支持范围的 CI 验证；若维护成本过高，应明确收窄依赖支持范围。

## 四、复现方法

在 RoboTenon 根目录，以安装了项目依赖的 Python >=3.10 运行：

```bash
python docs/changes/audit-2026-09-15/reproduce.py
```

脚本使用临时 SQLite 与内存 RPC 替身，不调用硬件。脚本断言的是本次审计观察到的缺陷；修复之后应修改为正确行为断言，再纳入正式测试。

**最终判断：可以明显提升模块化和可维护性，且无需推倒四服务架构。关键是统一状态与执行语义，再让目录和接口反映这些真实边界。**
