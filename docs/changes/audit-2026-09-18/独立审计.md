## Conclusion and scope

Retain the current division between the execution layer, task lifecycle, and explicit observability data sources. The assembly entry points could still bypass configuration, reuse resources after errors, and wait indefinitely during shutdown. Address these wiring and lifecycle issues before extending Coordinator recovery.

The audit independently inspected the code and reproduced failures. Earlier designs and documentation did not establish implementation correctness. The snapshot was the **uncommitted workspace** based on `e5c08cc599ead337a1a104c983aeab610f273d63`, including execution and observability changes. Several defects predated the parallel execution changes.

The review covered Runner/Worker/backends, TaskAdapter aggregation, application assembly, safety and Monitor, observability, Trace queries, and Web controls. Scope excluded GPUs, EGL, real models, robots, deployment networks, and a comprehensive security certification. No runtime logic changed, hardware was not connected, and existing services were not restarted.

## A01: The Monitor switch changes the source of safety state

Locations: `robotenon/runtime/runner.py:323`, `:376`, and `robotenon/runtime/factory.py:901`.

With `monitor_enabled=false`, Runner always constructed a new in-memory `SafetyStateStore` and injected it into the application. The factory then ignored the SQLite safety state in the main configuration. Setting `safety_state.require_shared=true` did not prevent this override.

The physical robot template combined `monitor_enabled=false` with shared SQLite safety state. Disabling active monitoring should preserve external safety signals, latched P3/P4 events, and shared storage constraints.

**Observed behavior.** A Fake Graph ran with a P4 latch already present in the configured SQLite database. SQLite still reported P4, but the execution context reported P0 and the Graph completed successfully. No hardware actions were issued. The test confirmed that the execution path did not use the external safety state.

**Repair.** Build and inject the explicitly configured safety state for both Monitor settings. The switch should control monitoring and polling only. Retain in-memory storage as an explicit option. Add end-to-end tests for the shared P4 at the Graph and Body boundaries.

A related ownership issue was that `factory.py:896` moved the safety path into the attempt resource directory. Configure ownership explicitly to distinguish task-local from device-wide, persistent safety state. Process mode alone should not redirect the location used by an external device to publish signals.

## A02: A configured Monitor is constructed but never participates in execution

Locations: `robotenon/runtime/runner.py:371`, `:377`, `:384`, `robotenon/runtime/factory.py:1034`, and `:1054`.

The factory constructed `app.monitors`, but Runner always passed `start_monitors=False`, created a legacy `SafetyMonitorService` without a checker, and supplied it to the Graph and Supervisor. The registered Monitor's resident polling never started, and named Graph requests never reached it.

**Observed behavior.** A Monitor supporting resident and request modes returned P4 on every check. A Graph running `monitor.request.audit` completed with zero plugin start and check calls. The case used a Fake environment and a Body that issued no hardware actions.

**Repair.** Use the application's `MonitorRuntime` as the Runner's monitoring object and connect it to both the Supervisor and Graph. Configure the default feedback checker as an ordinary registered Monitor. An entry-point integration test should verify both the plugin invocation and its safety effect.

## A03: Full Portal controls lack request-origin and identity checks

Locations: `robotenon/web/server.py:273`, `:284`, `:332`, and `:359`. Response CORS handling was near `:48`.

The POST handler read a length and parsed JSON without checking Origin, identity, or Content-Type. Submission, stop, rerun, and global shutdown shared this path. Responses also allowed broad cross-origin access.

**Observed behavior.** In a local test with a stub ExperimentManager, an external-origin `text/plain` POST received HTTP 200 and invoked `shutdown_all`. No actual manager or running task was affected.

The result confirmed missing server-side validation. Browser-level local-network protection depends on the browser and cannot provide a server-side identity boundary. The read-only mode disabled the affected controls.

**Repair.** Validate trusted Origin/Host for state-changing endpoints, require JSON and a session or startup-generated access token, and restrict CORS to explicit origins. Separate read and control permissions while retaining the common data-source protocol. Bound request-body sizes and read timeouts.

## A04: egl_device_ids is accepted but never applied

Location: `robotenon/runtime/parallel.py:200`.

`ExecutionOptions` accepted and validated `egl_device_ids`, and `ProcessSlot` supported it. When constructing a Slot, the backend passed profile, GPU, and options but omitted the EGL ID. Child processes inherited the environment without the requested mapping.

**Observed behavior.** For GPU `[0,1]` and EGL `[3,4]`, `egl_device_id` was None for both constructed Slots. No GPU was started. The test traced the missing parameter between configuration and execution objects.

**Impact.** Workers might render on the wrong device, fail to render, or concentrate load. Hardware behavior remained unverified.

**Repair.** Pass each explicit EGL ID to the corresponding Slot and preserve inheritance when unspecified. Add a test reading the child environment, then verify on actual EGL devices.

## A05: In-process tasks reuse a Tool after cleanup fails

Locations: `robotenon/runtime/worker.py:65`, `:77`, and exception handling for execute_case in `robotenon/task_adapters/evaluator.py`.

An error in `end_session` failed the current case, but WorkerRuntime only restored `_busy=false` and retained ToolRuntime. Evaluator continued to the next task, potentially reusing stale caches or connections. The process backend closed the Slot after an execution error, giving the backends different isolation behavior.

**Observed behavior.** A Tool that failed every `end_session` ran two cases sequentially. The events were `start → cleanup_failed → cleanup_failed → close`, showing reuse of the same instance. Both cases recorded errors.

**Repair.** Distinguish task failure from resource cleanup failure. Mark an affected Worker unavailable and close/rebuild it before the next task, or terminate the batch explicitly. Clearing the busy flag is insufficient. Apply this rule to the common lifecycle.

## A06: Observability shutdown waits indefinitely

Locations: `robotenon/infra/ingest_server.py:44` and `:59`.

After closing the listener, `close()` gathered all handlers without a deadline. A handler could still be waiting for another line from a client. Closing the listener did not close existing connections, so a silent client could hold close open.

**Observed behavior.** A temporary UDS connection sent no data. The close task waited until the test closed the client. The test used a short, controlled wait.

**Impact.** Shared observability shutdown, run termination, and resource-lock release could stall. Standalone daemons were also affected. Servers need a termination path independent of client cooperation.

**Repair.** Track connection writers, close active connections during shutdown, allow a bounded drain period, and cancel/reap handlers. Specify a shutdown budget for disk writes. Cancelling a coroutine does not stop a worker thread.

## A07: Colliding run_id values overwrite artifacts silently

Locations: `robotenon/runtime/experiment.py:140`, `robotenon/task_adapters/evaluator.py:214`, and the atomic-write helper `:23`.

The default run_id had second resolution and the output directory used `exist_ok=True`. No run reservation or existing-result check protected it. Runs started in the same second under one output root, or given the same explicit run_id, wrote the same global and episode paths. Atomic replacement protects individual writes but cannot isolate concurrent runs.

**Observed behavior.** Two sequential runs used the same configuration, root, and run_id. Both completed and the second replaced the original attempt_id in the episode file.

**Impact.** Prior summaries can be lost, traces can mix, and run identity ceases to be unique. At the time, there was no resume protocol authorizing this overwrite.

**Repair.** Add a random unique suffix to generated run_id values and atomically reserve the directory or lock before starting shared observability or writing files. Reject explicit duplicates by default. A future resume entry point should check version, configuration, and commit state.

## Recommended repair order

1. **Repair safety and assembly (A01, A02).** Apply safety state, Monitor, and Body configuration through the unified Runner. Include single physical-robot task paths in addition to parallel backends.
2. **Protect control entry points (A03).** Prioritize this before forwarding or sharing a full Portal.
3. **Align failure and shutdown semantics (A05, A06) and device binding (A04).** Backends may differ in scheduling and process isolation while sharing safety and resource cleanup contracts.
4. **Guarantee run identity and artifact isolation (A07).** Establish uniqueness before adding checkpoint resumption or takeover.

The following architectural improvements were proposed separately from the reproduced defects.

- **Assemble configuration once.** The Worker saved a loaded configuration, but initialize_application reloaded files per episode. Pass an immutable snapshot and hash to prevent old Tool/Graph definitions from mixing with new component lists. Add an integration test that edits configuration during a run.
- **Specify failure states.** Distinguish task failure, Graph failure, Worker loss, cleanup failure, and committed results. Preserve structured exceptions and tracebacks for diagnosis and retry decisions.
- **Bound query cost.** Read-only Trace SQL still called fetchall without a time or response-byte limit. Add a SQLite progress handler, row/byte limits, and cancellation to keep a large database from overwhelming the Web service.
- **Test configuration end to end.** The 179 tests missed the reported wiring failures. Verify that configuring a component or resource causes the actual entry point to use it, alongside registry and class-level tests.
- **Then add persistent scheduling.** Coordinator recovery needs task and attempt leases, heartbeats, a commit log, old Worker fencing, and reconciliation of side effects. Reading status.json alone cannot establish recovery.
- **Extend observability to meet measured requirements.** A durable outbox, Metrics deduplication, retention, indexing, and media aggregation need explicit throughput and reliability targets. Best-effort delivery supports debugging but cannot serve as the sole audit ledger.
