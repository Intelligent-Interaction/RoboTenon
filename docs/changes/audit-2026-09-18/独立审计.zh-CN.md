## 结论与范围

当前执行层、任务生命周期和显式观测数据源的职责划分可以继续沿用，但装配入口仍存在绕过配置、错误后复用和退出边界不完整的问题。优先修复这些接线与生命周期缺陷，再扩展 Coordinator 持久化恢复。

本次重新阅读当前代码并运行独立复现，不把之前的设计结论或文档当成实现正确的证据。审计对象是本地 `e5c08cc599ead337a1a104c983aeab610f273d63` 基础上的**当前未提交工作区**，包含执行与观测改造；不是只审计该 commit。问题包含既有实现缺陷，不全部归因于此次并行改造。

本轮检查了 Runner/Worker/执行后端、TaskAdapter 汇总、应用装配、安全与 Monitor、观测服务、Trace 查询以及 Web 控制接口。没有验证实际 GPU、EGL、真实模型、机器人或部署网络，也不是逐行覆盖全仓库的安全认证。本轮没有修改运行逻辑、连接真机或重启现有服务。

## A01：Monitor 开关意外改变安全状态来源

位置：`robotenon/runtime/runner.py:323`、`:376`；`robotenon/runtime/factory.py:901`。

`monitor_enabled=false` 时，Runner 无条件创建新的内存 `SafetyStateStore` 并注入应用。工厂因此不会采用主配置中的 SQLite 安全状态。`safety_state.require_shared=true` 也不能阻止该覆盖。

当前真机模板恰好同时配置了 `monitor_enabled=false` 和共享 SQLite 安全状态。关闭主动监测不应意味着忽略外部安全信号、已锁存的 P3/P4 或共享存储约束。

**复现：**在配置指定的 SQLite 中预写锁存 P4，运行 Fake Graph。SQLite 仍是 P4，但运行上下文报告 P0，Graph 成功完成。用例没有发出真实硬件动作；它确认的是外部安全状态没有接入此执行路径。

**修复：**无论是否启用 Monitor，都按明确配置构建并注入同一安全状态。Monitor 开关只控制监测实例/轮询。保留内存后端为正常配置选项，不能由监测开关隐式选择。补充共享 P4 对 Graph 与 Body 两个边界的端到端测试。

另一个应一并明确的边界：`factory.py:896` 会把 safety 路径改到 attempt 资源目录。任务独立安全状态与设备长期共享安全状态应通过显式资源所有权配置区分，不能只因进程模式就改掉外部设备正在发布信号的路径。

## A02：自定义 Monitor 被构造但没有参与执行

位置：`robotenon/runtime/runner.py:371`、`:377`、`:384`；`robotenon/runtime/factory.py:1034`、`:1054`。

工厂构建 `app.monitors`，但 Runner 固定传 `start_monitors=False`，随后自行创建未传 checker 的旧 `SafetyMonitorService`，并将后者交给 Graph 和 Supervisor。注册 Monitor 的 resident 轮询不会启动，Graph 的具名 request 也没有分派到该插件。

**复现：**配置一个同时支持 resident/request、检查结果固定为 P4 的 Monitor，并在 Graph 中执行 `monitor.request.audit`。插件的 start/check 调用次数都是零，Graph 仍完成。用例使用 Fake 环境和无硬件动作的 Body。

**修复：**让应用装配得到的 `MonitorRuntime` 成为 Runner 的监测对象，统一接入 Supervisor 与 Graph。需要反馈默认检查时，将其作为普通注册 Monitor 配置，而不是启动入口中的隐式替换。对“配置插件确实被调用并产生安全效果”增加入口集成测试。

## A03：完整 Portal 控制接口缺少请求来源和身份保护

位置：`robotenon/web/server.py:273`、`:284`、`:332`、`:359`；响应 CORS 见 `:48` 附近。

POST 处理器只读取长度并解析 JSON，不验证 Origin、请求身份或 Content-Type。提交、停止、重跑和全局关闭接口都走该路径；响应还使用宽泛的跨域来源设置。

**复现：**启动仅有桩 ExperimentManager 的本地测试服务，发送带外部 Origin 的 `text/plain` POST，服务器返回 200 并调用 `shutdown_all`。没有调用真实管理器，也没有停止任何实际任务。

这确认了服务端缺少控制请求校验。浏览器能否向本地端口送达此请求还取决于浏览器的本地网络保护，不能将其当作可靠防线；直接暴露在网络上的服务也缺少身份边界。只读模式禁用了这些实验控制接口，不受这条控制缺陷直接影响。

**修复：**为有副作用的控制接口校验受信 Origin/Host、要求 JSON 类型并使用会话或启动时生成的访问令牌；限制 CORS 到明确来源。只读查询与控制权限分离，保留相同数据源协议。请求体大小与读取超时也应有限制。

## A04：egl_device_ids 被接受但没有生效

位置：`robotenon/runtime/parallel.py:200`。

`ExecutionOptions` 接受并校验 `egl_device_ids`，`ProcessSlot` 也支持此参数，但后端构造 Slot 时只传 profile、GPU 和 options，没有传对应 EGL 编号。子进程最终沿用继承环境，不执行用户声明的映射。

**复现：**配置 GPU `[0,1]`、EGL `[3,4]`，创建后端后两个 Slot 的 `egl_device_id` 均为 None。没有启动 GPU；证据来自配置到执行对象的参数断链。

**影响：**Worker 可能在错误设备渲染，造成渲染失败或资源聚集；具体硬件表现尚未验证。

**修复：**将每个显式 EGL 编号传入对应 Slot，保留未设置时沿用环境的语义；增加子进程读取环境变量的测试，再进行实际 EGL 映射验证。

## A05：进程内任务清理失败后继续复用已污染 Tool

位置：`robotenon/runtime/worker.py:65`、`:77`；`robotenon/task_adapters/evaluator.py` 中 execute_case 的异常处理。

`end_session` 的异常会使当前 case 失败，但 WorkerRuntime 只恢复 `_busy=false`，不淘汰 ToolRuntime。Evaluator 捕获错误后继续下一个任务，因此工具清理失败后的缓存/连接仍可能被复用。进程后端遇到执行异常会关闭 Slot，两个后端的失败隔离语义不一致。

**复现：**构造一个每次 `end_session` 都报错的 Tool，顺序运行两个 case。事件为 `start → cleanup_failed → cleanup_failed → close`，说明第二个任务沿用了同一实例；两个 case 都记录错误。

**修复：**把任务业务失败与资源清理失败区分开。清理失败应标记 Worker 不可复用，在下一任务前完整关闭并重建，或明确终止批量；不能只清 busy 标志。此规则应用于统一生命周期，无需增加真机专用分支。

## A06：观测服务退出等待没有上界

位置：`robotenon/infra/ingest_server.py:44`、`:59`。

关闭监听后，`close()` 对所有连接 handler 无超时地 gather；handler 可能一直等待客户端的下一行。停止监听不关闭已建立连接，一个保持连接但不发送数据的客户端即可让 close 一直等待。

**复现：**连接临时 UDS 后不发送数据，调用 close；关闭任务持续等待，直到主动关闭客户端连接才返回。测试使用受控短等待，没有运行无限阻塞。

**影响：**共享观测关闭、运行退出和后续资源锁释放可能被拖住；外部 daemon 也受影响。正常 Worker 通常会关连接，但服务不能将对端配合作为唯一退出条件。

**修复：**跟踪连接 writer，停服后关闭连接，给在途写入有限的 drain 窗口，再取消/回收 handler。底层磁盘写入也要明确退出预算，不能把取消协程等同于已经终止工作线程。

## A07：run_id 冲突会静默覆盖已有产物

位置：`robotenon/runtime/experiment.py:140`；`robotenon/task_adapters/evaluator.py:214`；原子写入助手 `:23`。

默认 run_id 仅精确到秒；输出目录使用 `exist_ok=True`，没有运行目录预约或已有结果拒绝机制。同一输出根目录同秒启动，或显式复用 run_id，会写入相同全局文件和 episode 路径。原子 replace 只能避免单次半写入，不能防止两个运行覆盖彼此。

**复现：**使用相同配置、输出根目录和 run_id 连续执行两次；两次都成功，原 episode 文件的 attempt_id 被第二次替换。

**影响：**可能丢失旧汇总、混合新旧 Trace，并使 run 身份失去唯一性。当前并无 resume 协议，因此不能将这种覆盖理解为恢复功能。

**修复：**生成带随机唯一后缀的 run_id，并在启动共享观测和写任何运行文件前，原子预约运行目录/运行锁。显式同名运行默认拒绝；未来 resume 应验证版本、配置和提交状态后走明确接口。

## 建议的改进顺序

1. **先修安全和入口装配：A01、A02。**让安全状态、Monitor、Body 的配置在统一 Runner 中真实生效。真机单任务也受影响，不应仅验证并行后端。
2. **补上控制入口保护：A03。**尤其在完整 Portal 被转发或供多人使用前。
3. **统一错误与退出语义：A05、A06；修正设备绑定 A04。**后端差异应限于调度与进程隔离，不应改变安全依赖与资源清理的基本契约。
4. **保证运行身份与产物隔离：A07。**之后才适合增加断点恢复，避免在不唯一的 run 上叠加接管逻辑。

以下是进一步的架构改进，不计入已复现缺陷数量：

- **配置只装配一次。**目前 Worker 保存 loaded 配置，但每个 episode 的 initialize_application 又从文件加载。应传不可变配置快照与 hash，使长实验中途编辑文件不会出现旧 Tool/Graph 与新组件清单混用；另做运行中改配置的集成验证。
- **为故障状态建明确协议。**区分业务失败、Graph 失败、Worker 丢失、清理失败、结果已提交；保存结构化异常和 traceback，而非只传字符串，便于决定是否重试及排查根因。
- **限定查询成本。**Trace SQL 虽已只读，但仍直接 fetchall，没有执行时限和返回字节上限。增加 SQLite progress handler、行数/字节限制及取消，避免大型库拖垮 Web。
- **补端到端配置测试。**当前 179 项测试没有覆盖上述关键装配断链。围绕“配置一个组件/资源后，真实启动入口是否调用并使用它”设计矩阵，比继续只测注册表/单类更有效。
- **再建设持久化调度。**Coordinator 恢复需要任务与 attempt 的租约、心跳、提交日志、旧 Worker 隔离和副作用对账。当前缺失是已知能力边界，不应宣称已有恢复，也不应只通过重新读取 status.json 实现。
- **按实际需求增强观测。**持久化 outbox、Metrics 去重、数据保留期、索引和媒体聚合需要明确吞吐/可靠性目标。现有尽力投递可用于调试，但不能直接承担唯一审计账本。
