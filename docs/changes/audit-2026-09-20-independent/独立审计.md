# Independent audit of the RoboTenon workspace

[**English**](%E7%8B%AC%E7%AB%8B%E5%AE%A1%E8%AE%A1.md) · [简体中文](%E7%8B%AC%E7%AB%8B%E5%AE%A1%E8%AE%A1.zh-CN.md)

The system already had plugin assembly, Graph scheduling, process Workers, and observability. Reproductions exposed gaps in termination, task identity, model-output validation, and configuration consistency. Establish completion, confirmed stopping, and reliable outcomes before expanding parallel experiments or plugin coverage. Hardware deployment also requires action cancellation, synchronous driver isolation, and idempotency conflict handling.

The snapshot combined `3e23ae2067e913ff80720855ee77b0ca77d01150` with uncommitted changes, including the infrastructure plugin registry, Environment parameter forwarding, runtime, and tests. The audit inspected the implementation and designed fault cases before consulting prior reports. Documentation changed independently during the audit. Application code, configuration, tests, and build files matched the snapshot at final verification. See [source-manifest.json](source-manifest.json) for timestamps and digests of 396 files.

On macOS arm64 with Python 3.11.10 and Pydantic 2.13.5, the existing Python suite reported **440 passed, 1 skipped**, and JavaScript reported **20 passed**. The skip covered Linux native-renderer crash/preload integration. **All 11 new fault probes reproduced their respective defects.** The checks used isolated code copies, temporary data, fake drivers, or local child processes. They neither modified application code nor connected to a model service, GPU server, or robot.

**Priority findings**

P1 indicates an urgent fix or a prerequisite for the affected deployment. P2 indicates an important reliability improvement. These priorities are independent of runtime safety levels P0–P4.

**R01 — Portal stop confirmation misses separate Worker process groups**

Evidence: [experiments.py:224](../../../robotenon/web/experiments.py#L224), [experiments.py:263](../../../robotenon/web/experiments.py#L263), [parallel.py:66](../../../robotenon/runtime/parallel.py#L66), and [parallel.py:307](../../../robotenon/runtime/parallel.py#L307).

The Portal gave the Coordinator 3 seconds to exit. Workers created separate process groups with `setsid()` and had an internal cleanup budget of 10 seconds. The Coordinator handled SIGTERM through asyncio cancellation, but a blocked Worker could outlast the outer grace period. The Portal killed the Coordinator before Worker cleanup and reported release after checking only Coordinator exit.

The probe used the real process backend and a blocking fake TaskAdapter and returned `released=true / coordinator_exit=-9 / worker_state=Ss`. It established a surviving Worker. It did not test GPU or real model resource retention. Model group lifetimes suggest a risk of lingering resources and overlap with a subsequent experiment.

Give one owner responsibility for tracking and reaping Coordinator, Worker, and model groups. The outer grace period should allow internal cleanup, while independent cleanup must still work after forced Coordinator exit. Set `released`, release resources, and dispatch the next experiment only after confirming the full execution domain exited. Test blocked Workers, surviving model children, and forced Coordinator termination.

**R02 — Direct action cancellation does not send a low-level stop**

Evidence: [body.py:381](../../../robotenon/services/body.py#L381), [body.py:412](../../../robotenon/services/body.py#L412), and [body.py:489](../../../robotenon/services/body.py#L489). Graph stop cancels branches in [scheduler.py:354](../../../robotenon/workflow/scheduler.py#L354).

The CancelledError path in `execute()` ran an optional safe action without calling `_invoke_stop()`. With no safe action configured it returned interrupted and cleared `_active_task`. Later `close()` no longer triggered interruption. Even with stop_executor installed, cancelling execute and closing yielded `stop_calls=0` while the fake driver continued in its thread.

Use a common termination path for external cancellation, graph.stop, branch failure, and shutdown. Issue a bounded low-level stop, preserve its acknowledgement, and propagate external cancellation. Reject new actions while driver work is in flight. Verify callback and actual driver state in addition to `interrupted`.

**R03 — Model booleans require strict validation**

Evidence: [verify.py:96](../../../robotenon/modules/verify.py#L96) and [verify.py:123](../../../robotenon/modules/verify.py#L123).

`bool(output.get("subtask_success", False))` treated `"false"`, nonempty lists, and objects as true. With the current interface, `"false"` produced `subtask_success=True`, `completed=["pick"]`, and `remaining=[]`. This first affected STM and replanning. It did not establish that every environment would report final success.

Specify a Tool-output schema accepting only JSON boolean in the success field. For malformed input, return a diagnostic model-output error or UNKNOWN and retain the raw response for review. Cover false/true, strings, null, missing fields, and wrong types. Check that invalid inputs leave STM untouched. The previous audit script used an older `ctx.inputs` contract, so this check was rewritten for the current interface.

**R04 — Scheduling and persistence use different case identities**

Evidence: [base.py:51](../../../robotenon/task_adapters/base.py#L51), [evaluator.py:300](../../../robotenon/task_adapters/evaluator.py#L300), and [evaluator.py:576](../../../robotenon/task_adapters/evaluator.py#L576).

`TaskCase.key` used adapter/task/episode without index or seed. Artifact paths included seed and Trace identities included index. Two same-named cases sharing episode=0 with distinct indices and seeds passed path deduplication. On concurrent dispatch, the second overwrote `running[case.key]`. When the fast case completed, the scheduler lost its reference to the slower case and returned `completed=1 / total=2 / status=completed` with the latter still waiting.

Use one identity, such as adapter_id plus unique index, across scheduling, controls, traces, and results. Check uniqueness after enumeration and before side effects. Test duplicate rejection, concurrent seeds for one task, stop/rerun by index, and equality between the completion count and number of terminal cases.

**R05 — The RealRobotBody async wrapper conceals synchronous blocking**

Evidence: [real_robot_body.py:108](../../../robotenon/bodies/real_robot_body.py#L108), [real_robot_body.py:132](../../../robotenon/bodies/real_robot_body.py#L132), and [body.py:593](../../../robotenon/services/body.py#L593).

The parent saw async `_execute_action` and skipped synchronous isolation. The wrapper invoked `driver.execute()` before testing whether its result was awaitable. Synchronous execute/hold/health/start could therefore block the loop. A fake SDK slept for 120 ms, exceeded the 25 ms action timeout, and still reported succeeded. A 20 ms timer ran only after the driver finished.

Isolate synchronous methods at the actual SDK call, preserve in-flight guards, and keep the stop channel independent of blocked actions. Verify response budgets and failure escalation for execute, hold/stop, health, and start. Hardware still needs independent controller protection and evidence that motion stopped.

**R06 — The local-only trust model conflicts with default Compose port exposure**

Evidence: [access.py:9](../../../robotenon/web/access.py#L9), [server.py:38](../../../robotenon/web/server.py#L38), [docker-compose.yml:52](../../../docker-compose.yml#L52), and [docker-compose.yml:99](../../../docker-compose.yml#L99).

The Portal trusted localhost/SSH transport and ignored the supplied token. Host and Origin checks did not authenticate direct HTTP clients. The probe confirmed that control requests lacking Authorization passed the trusted-Host check. Compose published 8765/3000/9090/9100 without a host IP restriction. Grafana enabled anonymous Editor access and a default admin password.

For local access, explicitly bind published host ports to 127.0.0.1 or leave internal services unpublished. Provide a separate authenticated entry point and credentials for shared deployments. Require explicit controlled configuration for unauthenticated, non-loopback operation. Test both Host/Origin checks and actual listener/host publication scope.

This finding describes code and default configuration. No Docker service was started, network scanned, public reachability established, or intrusion observed. A container missing runnable configuration may limit available operations without providing authentication.

**R07 — Reloading configuration per task mixes versions within a run**

Evidence: [worker.py:92](../../../robotenon/runtime/worker.py#L92), [runner.py:526](../../../robotenon/runtime/runner.py#L526), and [factory.py:882](../../../robotenon/runtime/factory.py#L882).

Worker saved `loaded` and reused its Tool. An episode read parameters and Graph from that snapshot but called `initialize_application()` again using a configuration path. After the Echo Module parameter changed from before to after between tasks, the Worker's manifest still showed before while the second output returned after. A long run could combine old Tool/Graph with new Module/Body/Safety configuration.

Persist immutable merged configuration and its manifests on submission. Use the same snapshot for Workers, task assembly, and child processes. Explicit hot updates need a new configuration version and execution identity. Edit all source configurations between tasks in acceptance tests and verify that only new experiments use the changed values.

**R08 — Idempotency keys omit action content**

Evidence: [body.py:177](../../../robotenon/services/body.py#L177) and [actions.py:49](../../../robotenon/storage/actions.py#L49).

Success deduplication used only session/key. It neither stored nor verified a request digest. For target=1 then target=2 on the same key, the second call reported succeeded although only target=1 ran. A caller-side key collision became a false success acknowledgement.

Bind the key to a canonical digest of action type, payload, and target execution resource. Reject different business content for a reused key and return prior results for matching retries. Exclude volatile timestamps and attempt identities. Test in-memory cache, ledger restart, and conflicts. The physical completion-to-persistence gap still needs an UNKNOWN/reconciliation protocol.

**R09 — Observability ingestion shutdown has no deadline**

Evidence: [ingest_server.py:66](../../../robotenon/infra/ingest_server.py#L66). After listener shutdown, gather waited without a deadline for handlers still in `reader.readline()`. A silent client held close open for the observed 150 ms until explicitly disconnected.

Track writers, close connections on shutdown, drain within a budget, cancel remaining handlers, and define when storage threads are reaped. Test idle clients, partial messages, and failed writes. Observability cleanup must terminate.

**R10 — Worker stays reusable after cleanup failure**

Evidence: [worker.py:67](../../../robotenon/runtime/worker.py#L67). The finally block in `run_task()` reset only `_busy`. Failure in the Tool's `end_session()` left resident resources available. Two sequential tasks produced `start → cleanup_failed → cleanup_failed → close` with no second start, confirming reuse of the original instance.

Distinguish task failures from cleanup failures. Mark the Worker unavailable, then rebuild the Tool or terminate the Worker. Apply the same invalidation rules to both backends. Test cleanup exceptions, timeouts, and simultaneous application/cleanup errors.

**R11 — New runs do not reserve output identities atomically**

Evidence: [experiment.py:179](../../../robotenon/runtime/experiment.py#L179), [evaluator.py:254](../../../robotenon/task_adapters/evaluator.py#L254), and [evaluator.py:510](../../../robotenon/task_adapters/evaluator.py#L510). Default run_id used second resolution and existing directories were accepted. Two new submissions with the same ID replaced the original episode's attempt identity without a conflict error.

Add a unique random component to default IDs and atomically reserve the directory before shared observability or files are created. Reject duplicate new runs and use explicit, locked rerun/resume entry points. Preserve in-place Portal reruns with validated overwrite semantics.

**Implementation sequence and acceptance**

1. Fix R01, R02, and R03 first. Give the entire experiment one stop owner, confirm action cessation, and strictly validate model success. These affect resource release, physical state, and result credibility.
2. Address R04, R07, and R11 together. Align case, configuration, and artifact identities across scheduling, Trace, and controls.
3. Address R09 and R10. Bound shutdown and prevent automatic reuse after cleanup failure.
4. Complete controller-level acceptance for R05, R08, and R02 before hardware integration. Complete R06 before shared-network deployment.
5. Convert the 11 probes to positive regression tests. Add continuous verification of Linux process-group cleanup and supported Python/Pydantic versions. The repository had no committed CI configuration, and macOS checks did not exercise GPU or Linux native faults.

Clarify execution ownership first. The roughly 3395-line `web/experiments.py` handled queueing, process control, state repair, media resolution, and data projection. An execution control layer should own state, while the Web layer reads it and sends commands. R01 stop confirmation and R04 completion can then use one authority. Make configuration snapshots, model-output validation, and lifecycle interfaces common plugin contracts.

The six application plugin types, infrastructure provider registry, Graph scheduler, CAS checkpoints, and action ledger are suitable foundations. Add end-to-end contracts and fault tests. Set independent acceptance goals for Coordinator takeover, physical action reconciliation, observation freshness, and fixed multi-seed evaluation. Existing unit test results alone establish none of these capabilities.
