**Embodied systems review and RoboTenon project audit | 2026-09-20**

Maintenance note (2026-09-20). This report preserves the original evidence and conclusions. For subsequent plugin/infrastructure decoupling, see the [integration review](../plugin-extension-audit.md) and [infrastructure contracts](../../infrastructure-plugins.md).

The audit covered `robotenon/`, configurations, tests, and `embodied-design/audit-v2/具身系统设计方案-v2.1-融合版.md` in the workspace snapshot. `source-manifest.json` in this directory identifies the files. No application implementation changed and no robot, GPU server, or model endpoint was connected.

**Retain the layered architecture and position the project as an auditable embodied execution and experiment platform. Its strengths are Module boundaries, model reuse, fault isolation, and observability. Physical action contracts, verification quality, real-time control, and evidence from real tasks require more investment than additional framework features.**

A hardware adapter interface alone does not establish hardware acceptance. No matched comparison demonstrated an advantage of HLP + VLA + Verifier over VLA alone. Design v2.1 specifies fencing, physical reconciliation, and independent protection, but many of these requirements remained outside the default implementation.

Evidence is labeled **reproduced** for local observations, **static** for conclusions directly supported by code, and **historical** for archived experiment reports whose original server data was not reexamined. External systems were reviewed using official pages, authors' papers, and official repositories. The examples are representative. Vendor demonstrations do not establish this project's performance.

**2. Strengths to retain**

| Strength | Evidence | Value and scope |
|---|---|---|
| Distinct action and observation responsibilities | `services/body.py`, `services/environment.py`, `workflow/operations.py` | Default Graph actions pass through Body. Monitor observes and publishes findings. This centralizes checks and auditing but does not sandbox malicious plugins. |
| Resident Tools separated from task state | `runtime/worker.py`, `runtime/runner.py` | Workers can reuse models and connections while creating Environment/Module/Context per task. This suits batch evaluation with expensive VLAs. See A04 for the cleanup-failure exception. |
| Task-level and Graph-level parallelism are distinct | `runtime/parallel.py`, `workflow/scheduler.py` | Processes isolate native simulator crashes. Graph waves, dependencies, and routing have dedicated implementations. Concurrent Graph nodes do not establish physical resource independence. |
| Explicit recovery limits | `storage/context.py`, `storage/actions.py`, `docs/architecture.md` | Checkpoint/CAS, configuration fingerprints, and successful ack deduplication provide a foundation. The documentation makes no physical exactly-once guarantee. |
| Common observability identities | `runtime/observability.py`, `infra/observation_*` | attempt/worker/run identities and observation URIs support replay and diagnosis and keep image arrays out of context. Asynchronous telemetry is not a lossless evidence ledger. |
| Ongoing regression and incident records | 265 formal tests passed. Prior records cover Worker crashes and cache races. | These support engineering iteration beyond a single successful demo. The existing suite missed several reproduced cases. |

These are engineering gains over a single script connecting a model to env.step. No comparison was made with mature robot control platforms or leading foundation-model teams.

**3. Priority findings**

P1 identifies an urgent issue or a blocker for hardware integration. P2 identifies an important reliability or evaluation improvement. These audit priorities are independent of runtime safety levels P0–P4.

| ID | Priority | Trigger and impact | Evidence and recommendation |
|---|---|---|---|
| A01 | P1, hardware blocker | The async wrapper in `RealRobotBody` called synchronous `execute()` / `hold()` directly. A blocked SDK delayed the event loop, watchdog, and `wait_for` timeouts. | **Reproduced.** A fake driver blocked a 25 ms action for 120 ms. A 20 ms timer ran only after the driver returned, and the action reported succeeded. See `bodies/real_robot_body.py:108–149`. Parent `services/body.py:570` saw an async wrapper and skipped the synchronous-thread path. Isolate execute/stop/start/health, preserve the busy guard for in-flight threads, and validate stop confirmation with an independent local watchdog. |
| A02 | P1 | Verifier parsed success with `bool(output.get(...))`. A valid JSON string `"false"` evaluated as true and moved the subgoal to completed. | **Reproduced.** `modules/verify.py:98–127`. Use a strict schema/StrictBool. Return UNKNOWN or an error on malformed input, and keep free-form model text separate from physical facts. The environment success gate limits premature termination but cannot correct polluted STM or replanning. |
| A03 | P1, action and recovery contract | Body returned a previous successful ack for a different payload with the same session and idempotency key. The ledger had no request digest. | **Reproduced.** target=2 did not execute, but received the ack for target=1. See `services/body.py:170–179` and `storage/actions.py:49–52`. Bind the key to a canonical request digest, reject conflicts, and persist received/in-flight/unknown states and physical verification. Deduplication does not make an action physically atomic. |
| A04 | P2 | In-process cleanup cleared only `_busy` after failure, allowing the next sequential task to reuse the Tool. | **Historical defect reproduced.** `runtime/worker.py:90–104`. Mark the Worker poisoned, rebuild it or end the batch, and align isolation across serial/process backends. |
| A05 | P2 | On close, observability ingestion gathered handlers without a deadline. An idle connection could delay shutdown. | **Historical defect reproduced.** `infra/ingest_server.py:66–73`. Track and close connections, bound draining/cancellation/reaping, and specify when background writes finish. |
| A06 | P2 | Default run_id had second resolution. Without exclusive output reservation, repeated runs overwrote artifacts. | **Historical defect reproduced.** `runtime/experiment.py:140`, `task_adapters/evaluator.py:236`. Add a unique suffix and atomic reservation, reject explicit duplicates by default, and define resume independently. |
| A07 | P2, data quality | DatasetBuilder selected only succeeded episodes. It recorded `split_seed` but split sorted records by index%10. Adding episodes could move previous samples, and related tasks/scenes could cross train/test boundaries. | **Static.** `extensions/datasets.py:18–38`. Retain successful demonstrations and failure/correction data separately, group by scene/object/task family, freeze a split manifest, and use the seed for deterministic allocation. The audit identified leakage risk without establishing contamination of an actual dataset. |

Thread isolation for A01 would not establish hard real-time safety. Cancelling a Python coroutine cannot stop a vendor thread or reverse motion. Verify controller stop, physical evidence of stopped motion, and rejection of new actions.

**4. Gaps between design and implementation**

1. **Robot-side authority and action contracts.** Action/Chunk in `schemas.py:86–117` rely mainly on extensible dicts. `services/body.py:487` checks consistent chunk/action sessions and positive timeouts. The receiver still needs authority epoch, robot boot session, operation ID, plan version, release digest, joint order/units/frames, and state preconditions. `deadline_ns` uses Unix time, distinct from the intended robot monotonic-clock window. Define a controlled embodiment profile and gateway that reject stale authority/observations, reboot mismatches, clock anomalies, NaN/Inf, and invalid dimensions. Extensible metadata does not enforce these rules.

2. **Physical reconciliation and cancellation completion.** The ledger returned only persisted successful acknowledgements. A failure window remained between physical completion and ack persistence, and Coordinator automatic recovery was absent. RECONCILING, UNKNOWN outcomes, stop acknowledgement, and authority handover still needed implementation. Establish robot-local reconciliation before automatic retry or scheduler high availability. Disabling automatic retry in the hardware template is appropriate.

3. **Fresh world state.** ObservationFrame has time, age, and calibration fields, but a repository-wide search found no corresponding common action admission policy. `stale_observation_policy` was largely a schema. STM `physical_belief` was a model-updated dict without evidence, expiry, target identity, or uncertainty. Add observation source, synchronization window, and calibration version and distinguish observation, inference, prediction, and unknown state.

4. **Multi-rate execution.** The XR365 reference Graph used plan → action → body → observe → verify → evaluate and consumed queued actions while available. This aids debugging and regression, but lacks a complete protocol for overlapping inference/execution, constraining an executed prefix, and preserving continuity on chunk replacement. `RealRobotBody.control_rate_hz` was validated and stored without establishing a control period. Measure p50/p95/p99 observation age, inference latency, inter-chunk gaps, and missed deadlines before optimizing.

5. **Deployment configuration tied to real capabilities.** Hardware Body field `kind=ros2` is a label. A driver still must be injected. Template setting `heartbeat_ttl_s=3600` has not been validated for loss-of-connection protection. Use separate accelerated simulation, debug, and hardware profiles. Check the driver, stop capability, and watchdog settings at startup. Derive stop budgets from embodiment and scene acceptance tests.

6. **Release and learning cycle.** The release registry tracks state and content hashes. A hash alone proves neither signature, compatibility, nor acceptance. Version model, controller, action adaptation, normalization, cameras/calibration, and run configuration together. Add appropriately licensed and labeled failure, takeover, and recovery segments to datasets for offline training, fixed tests, shadow evaluation, and controlled release. Memory/Skill extensions provide building blocks, with no end-to-end continual-learning result established.

Run the complete fixed 317-task manifest and explain its relationship to the 365 in the benchmark name. Publish the task enumeration, exclusions, and reasons. Assign a deterministic seed per task, and use paired seeds for comparisons. Record first-attempt and eventual outcomes separately, including success, unmet goal, horizon, malformed model output, infrastructure crash, cancellation, and safety stop.

**Ablations for evaluating architectural contributions**

| Group | Condition | Question |
|---|---|---|
| B0 | Native upstream XR evaluation protocol | What reference performance do model and environment achieve? |
| B1 | RoboTenon VLA-only, identical weights and inputs | Does integration affect correctness or latency? |
| B2 | B1 + high-level planning | How does decomposition affect success and cost? |
| B3 | B2 + strict verifier and bounded recovery | Do errors, interventions, or replanning decrease within the budget? |
| B4 | B3 + asynchronous chunks or event-triggered replanning | What happens to throughput, responsiveness, success, and chunk transitions? |

Match tasks, seeds, weights, cameras, action transforms, horizon, wall-clock budget, and hardware. Align B0/B1 with upstream before testing policy improvements from B2 onward. Report paired success differences, confidence intervals, successful tasks per hour, completion time, intervention rate, verifier false-positive/false-negative/UNKNOWN rates, infrastructure failures, and inference cost. Use simulator ground truth for independent evaluation and label any runtime termination oracle explicitly.

**6. Implementation order and acceptance**

| Order | Work | Acceptance criteria |
|---|---|---|
| 1: Current development cycle | Repair A01–A06 and include A07 in dataset construction | Convert reproductions to positive regression tests. A synchronous SDK must not block the control loop. Reject string false, mismatched payloads for one key, and duplicate runs. Retire resources after cleanup failure and bound shutdown. |
| 2: Establish a baseline | Complete 317-task regression and paired B0/B1 comparison | Freeze the manifest and document inclusions/exclusions. Separate first attempts from retries and task outcomes from system errors. Preserve traceable artifacts without overwriting them and complete the full run. |
| 3: Before hardware | Single-embodiment profile, command gateway, authority and observation validity, stop confirmation and reconciliation | Test stale epoch/session, clock anomalies, delayed observations, lost ack, partial execution, disconnection, and human takeover with a fake driver and hardware in the loop. UNKNOWN must not automatically replay a side effect. |
| 4: Capability improvements | B2/B3 and event-driven high-level decisions, then measured multi-rate changes | Demonstrate reproducible success/throughput gains within equal budgets. Validate verifier errors and recovery budgets. Chunk replacement affects only the unexecuted suffix, and late inference cannot regain control. |
| 5: Learning cycle | Failure/correction segments, frozen grouped datasets, and versioned releases | Trace failures to samples, candidate models, and regression results. Verify rollback and compatibility checks. |

These stages express dependencies, without implying delivery estimates. Defer multi-robot scheduling, large messaging platforms, general-purpose world models, and autonomous skill releases until measured throughput, recovery, or data requirements justify them.

**7. Verification record and limits**

- Formal suite on Python 3.11: **all 265 passed**. A separate collect-only run confirmed the count. The default `python3` was 3.9 and lacked pydantic. Collection initially failed because the project requires Python≥3.10, then succeeded in the existing 3.11 environment.
- New audit reproductions: **3 passed**, asserting that A01, A02, and A03 existed.
- Historical rechecks: **3 passed, 4 deselected**, confirming A04, A05, and A06. The reproduction files in the two directories have the same name and should be run separately to avoid pytest default-import collisions.
- No GPUs, real VLAs, or physical robots were tested. Historical server experiments are identified as supporting evidence. The audit did not perform full security certification, penetration testing, or exhaustive plugin compatibility assessment.
- New files comprised this report, the reproduction script, and the source manifest. No application fixes were mixed into the audit.
